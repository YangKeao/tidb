# Rust TiDB 复用原版 TiKV 表达式执行器

## 固定版本

TiDB 候选是本地分支 `expression-tidb-only` 的产品提交 `dbedcc118028b294c15165406f0c38f2ef029033`。原始 TiDB 基线为 `364aef2bab5cc633ecb76a775ae8f36f86a6687d`。TiKV 固定在原版 `548812e1ef57aef077a2062a9cc356640a6347f5`，仓库改动为零。Cargo 解析图中的 22 个 TiKV 包均来自官方 Git，逐文件重算的 382 个源码摘要匹配 Git 树 `2673e3f6e3e395e3a54103ff663efa41fad7a19a`。来源核对见 `verified-upstream-pin-proof.json` 与 `verified-cargo-graph.log`。原双仓候选 TiDB `25cc03dde3` 与 TiKV `57127f26bd` 保留供对照。

TiDB 产品差异共新增 14,535 行、删除 11,778 行，合计 26,313 行，范围全在 `rust/`。扣除 Cargo.lock 和文档后新增 12,543 行、删除 11,682 行，合计 24,225 行。汇总包含源码、测试和构建声明。逐文件口径见 `verified-product.numstat`。原双仓候选按相同基线与口径累计增删 38,965 行，扣除锁文件和文档后为 36,084 行。

## 执行方式

TiDB 本地类型化表达式、SQL 算子与进程内 Unistore 都使用原版 `RpnExpression::eval_decoded`。普通 SQL 函数从公开 PB 构建器取得 TiKV 已注册的回调，TiDB 专有语义在同一程序内使用回调访问语句和会话。分支回调只对确实选中的行执行子程序。物理整数和字节列走选行读入，Decimal 适配在列实际被访问时进行，同批重复访问复用已转换值。

Unistore 把完整 PB 表达式交给上游构建器，保留签名校验、短路判断、相邻逻辑展平及深度门槛。TiDB 在产物上适配物理列读取和原有整数除零诊断。本地 SQL 的 Decimal 适配区分内部系数与 SQL 结果标度，并纠正原版负数乘零时丢失标度的问题。Decimal 的公开 Chunk 编解码布局固定于上述 TiKV 提交，标度往返回归同时保存内部系数与可见小数位。Decimal 字符转换使用 SDK 对完整系数的原有格式化。模式缓存只缓存字面量模式及选项，延迟绑定的逐行模式由对应行提供。

补充回调随 TiDB 进程运行。远程 TiKV 对网络下推继续使用自带 PB 构建器及原内核，进程内 Unistore 也保留原版 wire 内核的算术语义。此交付验证了实际本地 DAG 请求与历史 SQL 的共享远程存储。两臂共用的历史 TiKV 服务二进制为归档构建，候选的 Rust 依赖来源以 Cargo 证明为准。

- 真实 MySQL 客户端的 40 项短路、RAND 与诊断探针覆盖 97 行、初始 Chunk 1 或 32 和两档向量开关。37 条回放包含建表、128 行显式写入和实际查询，输入在 `unified-restart/route-replay.sql`，比较字段为逐条结果行、客户端协议类型码、错误码及消息、以及有序告警。37 项与上次双仓候选一致，原始 Rust 有一条条件 RAND 的行结果不同，128 行里有 46 个取样值不同，两列 HOUR 相同。其余 36 项一致。
- 11/20 的 Session 直连观测还比较了内部 Datum 的载体符号，因此识别出 CRC32 的载体差异。本次协议读回记录同时保留 CRC32 数值及协议类型码。独立调试器回放确认同样 37 项，并记录了 499 次 RPN 宿主节点调用和 1,940 次本地值实现的逐行调用，含建表等初始化。前者可一批一调，后者逐行计数，二者也具有包含关系。
- 复审用例覆盖跨度 36 的同运算符和交替逻辑树，与上游编译产物一致。真实 Unistore 请求通过显式 Enum 与 BIT 字面量筛选，格式有误的短路死分支照常报签名错误。整数严格除零、告警及死分支的真实请求测试通过。
- 两档向量开关及 `div_precision_increment=0/4` 的 20 个 Decimal 观测与双仓定版及 Go 完全一致。涵盖零乘负数、`CAST AS CHAR`、IF、派生 Chunk 和后续乘法。`CHAR(2)` SELECT 返回 12、-0、NULL 并产生两条 1406 告警。严格 INSERT SELECT 报 1406 且无写入，两档向量开关均与双仓定版和 Go 相同。原始 Rust 和修前候选曾以告警继续写入三行。
- typed Chunk 中，文本为 a、延迟模式两行分别为 a 与 b 时返回 1 和 0。此前同一用例误返回 1 和 1。字面量模式持续返回 1。修订后准入使用与执行参数专用逻辑相同的字面量判定。

## 性能核对

历史微基准按 10/16 形状复测。每端配对三次进程，在 CPU 2 运行 13 种函数 × 5 个批宽，另测 6 项单行 AST 和 6 项单行 typed Chunk。批宽 1 的 13 项均变慢。批宽 1,024 时，ABS、IF 和 STRCMP 分别为原始版耗时的 0.204、0.329 和 0.286 倍。Decimal 加法和 REGEXP_LIKE 分别为 3.515 和 2.805 倍。单行 AST 在计时前准备程序，单行 typed Chunk 和批量表的时钟包括结果物化。绝对值、倍率和路由在 `wiki-micro-verified/tables.zh.md`。

另在 CPU 23 用同一夹具实测两个类型化投影算子。每格五轮中位数，单位 ns/行。

| 表达式 | 批量，原始 → 候选 | 逐行直接调用，原始 → 候选 | 已准备程序的标量投影，原始 → 候选 |
| --- | ---: | ---: | ---: |
| 嵌套 BIGINT 算术 | 37.941 → 27.777 | 175.023 → 5,302.472 | 182.401 → 833.418 |
| HOUR(IF(...)) | 307.895 → 55.232 | 287.632 → 3,326.178 | 309.165 → 615.218 |

逐行直接调用包含每次表达式准备。持有已准备程序的标量投影也变慢。以上是固定夹具上的求值结果。历史端到端 SQL 表包含计划、存储及客户端取回。

历史端到端 SQL 按 11/06 的 48 格复跑。用 8,192 行的同一派生表，两端共用同一归档版远程存储服务。两个前端均为 release、thin LTO 和 glibc 分配器，实际初始和最大 Chunk 分别为 32 与 1,024 行，向量化开启。48 格的返回行、列类型、告警和设置都一致。执行计划的算子及属性一致，其中 42 格的估计行数有差异。

四轮交替了两端顺序。原始记录包含 384 个计时窗口、266,960 次查询，时钟包括完整提取结果。48 格的同轮 p50 倍率中位数为 1.004，范围 0.723–1.158。6 个单行 SQL 的倍率为 0.998–1.079。返回 4,096 行的典型算术、Decimal、JSON 和 Unicode 正则样本分别为 1.009、1.004、0.916 和 0.723 倍。完整三表、p95、吞吐和原始采样见 `wiki-sql/tables.zh.md`、`summary.json` 和 `primary.jsonl`。

首次 SQL 预检缺少历史派生表，两端均返回表不存在。补建并核对数据后才开始正式计时。首轮拒绝及实际建表方法保留在 `wiki-sql/initial-preflight-no-derived.json` 和 `derive-fixture.py`。
