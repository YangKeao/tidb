# 表达式复用整体设计复审：以约10K改动为目标

2026-11-13。审查固定TiDB `15deabe45576f67a1210ee357dbf1a21dd6cd4d7`、TiKV `f7672bf980143f2938fd0f900650a4c29091e70f`；原始基线分别为`364aef2bab5cc633ecb76a775ae8f36f86a6687d`、`548812e1ef57aef077a2062a9cc356640a6347f5`。这是设计审查与建议，没有实施架构替换。

结论：应改变复用边界，直接共享类型化的函数内核，让各引擎现有执行器负责表达式调度。当前方案同时扩展了类型兼容、第二种表达式构建接口、编译证明、宿主任务协议和执行模式，随后又为这些接口建立大量测试。继续保留这些边界而合并内部重复代码，不足以从数十万行降到约10K。此前最后一轮“剩余逻辑有保留理由”的结论只针对既定接口下的局部清理，不能证明这些接口在新设计中都需要存在。

## 2. 四个设计问题

**函数复用被扩大成了执行框架复用。** TiDB `evaluator/batch.rs:7090`的`compile_calculation_profile`会根据来源与类型创建主program，并可能额外创建row、Decimal fast及deferred profiles。`NativeView`在225行有15种变体。SDK `local/compile.rs:24`又区分Row、ControlLineage、SqlBatch、EvaluatedAscii、EvaluatedBytes五类入口。来源差异确实存在，但不意味着每种来源都需要新的编译及运行协议。

**已准备好的值仍要经过程序化包装。** SDK `local/batch.rs:9545`的`prepare_evaluated_bytes`为固定operation编译小程序，验证固定形状，建立`EvalContext`和worker。TiDB `tikv/ready_value.rs:1656`再管理缓存或一次性调用。对于已经取得参数的纯函数，这些结构不是共享函数体的必要条件。并非所有函数现在都走这条链，已有直接调用共享内核的路径。

**同进程类型边界被设计成了带身份认证的任务传输协议。** TiDB `evaluator/batch_values.rs:26`将原生值保存在表里，用40字节的namespace/generation/index/version/role句柄穿过Bytes载体；`batch_hosts.rs`维护metadata、demand和task状态；SDK `types/expr_eval.rs:3581`维护包括Host、Ordinary、RowHostScope在内的帧。在现有可回调、可重置的协议中，来源与代次检查有必要。正确的简化是删除不需要的协议，用词法借用和拥有的类型化结果替代，不能保留任务和裸句柄却删认证。

**“共享owner”并不自动消除两套语义。** 例如TiDB `mydecimal.rs`保留原40字节布局和写回语义，SDK另有`native_mydecimal.rs`；SHA2 native与wire的无效长度告警也不同。为了兼容原行为，把native变体迁到TiKV，仍会增加兼容代码。不能把所有Native后缀都判成重复，也不能通过统一为wire语义来默默改变SQL行为。

## 3. 建议采用的边界

    TiDB现有求值/批量调度 ── 参数转换 ─┐
                                     ├── 同一个类型化函数内核
    TiKV现有RPN wrapper ── 参数转换 ──┘

共享内核接收真正的值或借用，如整数、字节切片、Decimal引用，以及该函数确实需要的语义参数。它不接收表达式、HostSlot、task ID、伪装成Bytes的值句柄或任意求值回调。NULL和错误使用类型化返回；缓存只属于真正需要准备状态的函数，例如正则表达式，不能为每个普通函数创建worker。

这不是一个尚不存在的抽象要求：TiDB `tikv/crypto_value.rs:155`的`body`已经调用SDK `native_crypto_value.rs:68`，后者在MD5/SHA分支直接进入`impl_encryption`中原有函数。`impl_encryption.rs:206`的MD5函数体本身同时用于RPN包装。可以沿这个边界保留SQL参数转换，去掉外围调度往返；不能将MD5的可行性直接外推为所有245个family都能零成本替换。

| 当前部分 | 建议 | 必须保留的行为 |
| --- | --- | --- |
| local IR、profile、closed-source snapshot、ready-value小程序 | 普通值函数不再经过；由现有表达式准备过程确定函数和参数类型 | 非法输入在入口拒绝，错误不触发旧算法回退 |
| Host start/resume/cancel和40字节句柄 | 将求值状态留在宿主执行器，直接借用参数/移动结果 | 按需求值、异常清理、真实回调边界验证 |
| 多套来源与row/window适配 | 各来源只完成一次入口适配；共享同一值函数，批量循环复用该函数或已有vector kernel | selection重复/乱序、NULL、输出类型和现有向量优化 |
| Decimal/JSON/时间/字符集兼容 | 逐项决定复用既有类型还是小型显式转换；保留真正不同的策略 | 精度、溢出、编码、collation、时区和可观察错误 |
| 实验API、路由计数和历史矩阵 | 保留在封存实验分支；新产品设计只带必要公开入口及少量诊断 | 历史证据可追溯，不把搬走代码算作逻辑消除 |
| 大量协议/入口排列测试 | 协议消失后删除只测试该协议的用例；真实SQL反例归入共享数据表和现有测试套件 | 边界、短路、缓存、错误及旧问题的独立预期值 |

此前“先保留通用宿主协议和实验接口”的指令是分阶段安排（Raft d286c74f）；本次重新审查建议改变这些边界，但没有擅自删除现有接口。人类6129cd47要求统一接入并避免性能损耗，不应解释成“每个函数都必须进入同一个新RPN循环”。本建议统一函数实现和适配方式，保留TiDB/TiKV各自的表达式调度；不再承诺所有入口只有一个执行循环，这是明确的架构取舍。

用户早先2979a576已允许放宽warning/error顺序。新设计不应重新要求全部历史排序一致；但顺序放宽不授权多执行短路分支、丢告警、改变返回值或副作用次数。现有测试中仅用于固定内部顺序的断言应与语义断言分开审查。

## 4. 10K目标的可行性与工作顺序

必须同时报告“新增”“删除”“净增”和“新增+删除”，并将两个仓库、生成代码、测试一起算清。把实现移到新仓库、生成后不计入、切成多个PR，均不能证明全项目达标。

如果10K严格指相对原始基线的**新增+删除总行数**，当前已经保留的47,904行删除本身就超预算；保留同样删除集合便不可能达到10K。若指**净新增维护代码**，则可以把约10K设为重设计预算，但当前审查不能证明全函数范围和既有兼容语义能够同时落在这个预算内。仅把测试排除出数字也不算完成目标。

建议从原始基线建立独立候选，选择性带回共享内核，保留现分支与证据供对照；避免先在当前分支继续删除几十万行、再不得不恢复依赖。候选中恢复的是宿主调度，不是重新保留已迁移函数的第二份算法。函数在静态接线时选择确定的实现，运行失败不得重跑旧实现。

先用三条完整调用链验证边界：MD5（纯值函数）、Decimal算术（表示和溢出）、IF包住会报错的JSON/转换表达式（按需执行）。每条覆盖AST、typed、适用的PB/Unistore入口、单行和批量，分别记录需要增加的适配与测试行数。必须证明主路径不再经过LocalExpr/HostTask/NativeValueStore，而非新增一条可选快路径留下全部原实现。

随后按真实共同语义扩展到其他family，合并行/批量转换和错误投影；每迁移一类同步核销其旧adapter、专用状态和协议测试。复杂类型是达到体积目标的主要不确定性，应在扩大覆盖前验证，不能只凭几十个简单函数推算。10K可先分配为约6K实现、3K测试、1K接线/配置的设计预算，这是约束而不是已验证的工期或行数估计；删除量仍另报，严格总改动也同时计算。

验收必须包括当前已覆盖功能和原始行为反例、短路/NULL/错误集合、状态函数与缓存生命周期、真实SQL的单行及批量CPU/延迟；对照同时保留原始实现与当前保留版，同版重复测量估计波动。不能由更少代码直接推出更快，也不能因为共享内核就宣称每个执行器性能相同。若代表性复杂类型已明显突破预算，应报告“全范围+兼容+10K”的冲突，重新评估范围或语义边界，而不是新增一层通用框架掩盖它。
