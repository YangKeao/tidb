# 表达式复用整体设计复审：以约10K改动为目标

2026-11-13。审查固定TiDB `15deabe45576f67a1210ee357dbf1a21dd6cd4d7`、TiKV `f7672bf980143f2938fd0f900650a4c29091e70f`；原始基线分别为`364aef2bab5cc633ecb76a775ae8f36f86a6687d`、`548812e1ef57aef077a2062a9cc356640a6347f5`。这是设计审查与建议，没有实施架构替换。

结论（按2026-11-13人类1214f3b7澄清修订）：必须共享完整表达式求值内核，包括表达式组合、参数需求、短路和批量执行，不能退化为只共享函数体、保留两套表达式求值器。上一版的推荐缩窄了目标，现撤回。简化应围绕一个共享求值器，消除重复表示、分层编译证明和逐节点宿主任务往返。约10K仍是设计目标，不以放弃共享内核换取行数。

当前已存在共享RPN帧循环，并不是两个完全独立的新求值器。问题在于围绕这个循环叠加了多种构建入口、来源profile、值载体和恢复协议，以及相应的组合测试。此前最后一轮“剩余逻辑有保留理由”的结论只针对既定接口下的局部清理，不能证明这些接口在重新设计后都需要存在。

## 2. 四个设计问题

**共享执行内核外围存在多套表达与准备路径。** TiDB `evaluator/batch.rs:7090`的`compile_calculation_profile`会根据来源与类型创建主program，并可能额外创建row、Decimal fast及deferred profiles。`NativeView`在225行有15种变体。SDK `local/compile.rs:24`又区分Row、ControlLineage、SqlBatch、EvaluatedAscii、EvaluatedBytes五类入口。来源差异确实存在，但不意味着每种来源都需要新的编译及运行协议。

**已准备好的值仍要经过程序化包装。** SDK `local/batch.rs:9545`的`prepare_evaluated_bytes`为固定operation编译小程序，验证固定形状，建立`EvalContext`和worker。TiDB `tikv/ready_value.rs:1656`再管理缓存或一次性调用。对于已经取得参数的纯函数，这些结构不是共享函数体的必要条件。并非所有函数现在都走这条链，已有直接调用共享内核的路径。

**同进程类型边界被设计成了带身份认证的任务传输协议。** TiDB `evaluator/batch_values.rs:26`将原生值保存在表里，用40字节的namespace/generation/index/version/role句柄穿过Bytes载体；`batch_hosts.rs`维护metadata、demand和task状态；SDK `types/expr_eval.rs:3581`维护包括Host、Ordinary、RowHostScope在内的帧。在现有可回调、可重置的协议中，来源与代次检查有必要。正确的简化是删除不需要的协议，用词法借用和拥有的类型化结果替代，不能保留任务和裸句柄却删认证。

**“共享owner”并不自动消除两套语义。** 例如TiDB `mydecimal.rs`保留原40字节布局和写回语义，SDK另有`native_mydecimal.rs`；SHA2 native与wire的无效长度告警也不同。为了兼容原行为，把native变体迁到TiKV，仍会增加兼容代码。不能把所有Native后缀都判成重复，也不能通过统一为wire语义来默默改变SQL行为。

## 3. 修订后的共享内核边界

    TiDB AST / typed expression ── 薄的构建适配 ─┐
                                               ├── 同一种已验证程序表示
    TiKV PB expression ─────────── 薄的构建适配 ─┘
                                                       │
                                                       ▼
                                      一个共享表达式执行内核
                                  参数需求、短路、批量与函数计算
                                                       │
                                                       ▼
                                        类型化结果和诊断

两侧仍有各自的存储/SQL executor，但它们只能向共享内核提交表达式程序与输入批次，不能保留另一套表达式树遍历或短路求值。TiDB与TiKV的源语法和wire编号可以不同；入口适配将确有区别的语义落实为明确的函数签名、类型和必要策略。差异不应扩散为每个来源一套恢复状态机，也不能假装所有AST/PB语义本来完全相同。

**优先收敛现有RPN表示与帧循环，不再发明另一套IR或VM。** SDK `types/expr.rs:18`已有函数、常量、列以及控制调用节点，`types/expr_eval.rs:3696`已有一个`eval_frames`处理嵌套计算。保留这些必要能力；让TiDB和PB构建器通过一个受约束的构建接口产生该程序，合并`LocalExpr → facts/snapshot → profile → RPN`之间重复证明相同结构的步骤。程序在构建完成时验证并冻结；每批验证输入布局，不能每层重新复制、认证同一份描述。

**共享内核必须自己决定何时求哪个子表达式。** IF/CASE/COALESCE、NULL停止、强制转换及诊断相关需求都应在共享节点/函数执行中处理。TiDB不能通过`start/resume`把参数求值与转换次序再实现一遍。宿主接口只提供确实外部的输入或能力，如列/参数读取、时区、SQL mode、语句时间、变量与warning sink；必要副作用在内核实际需求时调用。接口不提供“求值这个子表达式”的回调，也不把所有函数伪装成宿主函数。这意味着部分当前TiDB里的coercion和控制逻辑必须真正迁入共享层，是需要验证的重构工作。

**只保留一种共享值传递机制。** 在边界将输入绑定为内核认识的类型化值/列视图，内部不再把TiDB Datum转为40字节Bytes句柄、查表取回再转换。优先复用现有ScalarValue/VectorValue与共享datatype；完整SQL FieldType不能丢，Decimal、JSON、Raw/hybrid等不兼容表示需要逐项确定无损桥接。不能通过string/f64中转或提前转换未选分支来减少代码。只读借用与明确结果所有权应承担内部生命周期约束；真实外部回调返回的数据仍需边界检查。

**行和批量是同一内核的输入规模，不是两个完整program。** 单行也进入共享执行入口。已有向量kernel可在同一调度器中处理一批数据；短路节点只调度选中行/子节点，必要的有副作用计算保留其需求次序。不能为了接口统一强迫所有批量退化成逐行，也不能强迫未访问分支提前求值。是否能移除当前row/bulk/Decimal-fast成套profile，要由统一表示及相应验证支持，而不是直接删快路径。

| 当前部分 | 重新设计后的职责 |
| --- | --- |
| 多套local编译入口与source snapshot/profile | 一个共享程序构建与验证过程；必要来源语义作为明确数据 |
| TiDB逐函数demand/task与SDK host恢复配合 | 参数需求、短路及转换归共享执行内核；宿主只提供外部能力 |
| NativeValueStore及Bytes句柄 | 类型化输入/输出、借用与结果所有权；保留真正边界检查 |
| ready-value函数小程序/worker | 已在共享程序中的函数直接进入内核计算，不再嵌套准备另一份固定程序 |
| 行、批量与诊断的成套适配 | 同一个程序与执行入口；保留必要向量化及有副作用的需求规则 |
| 实验入口与协议排列测试 | 最小产品接口；共享语义用例同时覆盖两侧入口，删除消失协议的专属测试 |

当前crypto直接调用共享函数体，只能说明函数体内部不必再绕一层worker，不能证明保留两套表达式调度符合目标。保留函数共享的成果，同时使上层表达式组合也进入同一内核。

此前人类d286c74f允许暂时保留通用宿主协议和实验接口；本次整体审查可以提出替代方案，但尚未删除它们。最新1214f3b7明确要求共享表达式内核，优先于上一版报告中“各自调度”的建议。早先2979a576允许放宽warning/error顺序；不因此多执行短路分支、丢告警或改变副作用次数。

## 4. 10K目标的可行性与工作顺序

必须同时报告“新增”“删除”“净增”和“新增+删除”，并将两个仓库、生成代码、测试一起算清。把实现移到新仓库、生成后不计入、切成多个PR，均不能证明全项目达标。

如果10K严格指相对原始基线的**新增+删除总行数**，当前已经保留的47,904行删除本身就超预算；保留同样删除集合便不可能达到10K。若指**净新增维护代码**，则可以把约10K设为重设计预算，但当前审查不能证明全函数范围和既有兼容语义能够同时落在这个预算内。仅把测试排除出数字也不算完成目标。

建议建立独立候选，保留当前分支和证据。以现有RPN程序、控制节点及帧循环为出发点抽取最小共享内核；两侧只接薄构建和数据/上下文适配。不恢复TiDB自己的表达式求值器，不建立“新内核失败后回旧内核”的运行时回退。与原始项目基线持续统计差异，避免只看相对当前分支删掉多少。

先用三条完整调用链验证这个架构：MD5（普通函数）、Decimal算术（表示和溢出）、IF包住会报错的JSON/转换表达式（按需执行）。每条通过TiDB和TiKV适用入口，覆盖单行与批量。验收证据必须说明它们由同一个程序类型和同一个执行内核完成，TiDB不再通过host恢复协议控制子表达式；两端语义完全相同的情况才要求完全相同的程序/结果，不把真实语义差异掩盖成接入成功。

随后迁移其余family，并同步删除被共享内核接管的宿主demand、profile适配和值句柄。测试以共享语义矩阵加两侧入口绑定测试为主，不继续为多套内部协议做笛卡尔积。先用复杂类型及短路链证明表示和职责能收敛，再估算全范围体积；当前没有依据承诺完整共享表达式内核、全兼容和约10K能够同时达到。

验收必须包括当前已覆盖功能和原始行为反例、短路/NULL/错误集合、状态函数与缓存生命周期、真实SQL的单行及批量CPU/延迟；对照同时保留原始实现与当前保留版，同版重复测量估计波动。不能由更少代码直接推出更快，也不能因为共享内核就宣称每个执行器性能相同。若代表性复杂类型已明显突破预算，应报告“全范围+兼容+10K”的冲突，重新评估范围或语义边界，而不是新增一层通用框架掩盖它。
