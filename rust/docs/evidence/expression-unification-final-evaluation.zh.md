## 功能与范围

- 冻结分母仍为 245 个函数族，保守保留已有 240 个 TiKV-only 算法迁移信用，即 97.959%，超过原定 221 个的门槛。没有新增别名信用或缩小分母。完整 281 行清单及原始排除项见 `final-coverage.json`。
- 五个已登记的兼容算法仍由 TiDB 拥有：JSON_SCHEMA_VALID、TIDB_DECODE_PLAN、TIDB_DECODE_BINARY_PLAN、TIDB_ENCODE_SQL_DIGEST、VALIDATE_PASSWORD_STRENGTH。它们全部保持未计分；只接受值/上下文的明确适配，不在错误后重跑 native。动态真实列输入的五组新旧服务对照均通过。
- 公共 Expression / ScalarFunction、解析 AST、typed/native batch、Suite、Projection / Expand、过滤及 Unistore 的真实 SimpleExpr / Shared 子表达式均接入同一个 SDK 编译与执行模型。TiDB 保留 SQL 前端、执行器调度、元信息和宿主原语。没有伪造 Expression、SQL 类型或来源所有者。

## 测量方法

- 对比冻结原始 native 前端 364aef2bab5cc633ecb76a775ae8f36f86a6687d 与当前 Rust 前端，均为 release、相同编译器、关闭默认 allocator feature。Go TiDB 只创建真实 TiKV 数据，随后停止；所有测量通过 Rust MySQL 端点。
- 两个前端共用同一真实 PD / 当前 TiKV、同一 8192 行表。TiKV 为 dev/unoptimized 构建，因此这些数字是受该存储条件影响的本机实验，不是生产容量。
- 前端固定四个不同物理核 2–5，TiKV 的全部线程固定 6–7，PD 固定 8–9；单客户端固定 10。并发使用独立客户端进程和单独的四个物理核。
- 查询读取完全相同的 4096 行；另有真实单行点查。计时包含解析、准备、RPC、结果编码及客户端完整取回。三轮按 native/current、current/native、native/current 交错；每格至少 20 次与 0.5 秒，单格最多 1000 次。没有编译、测试、profiler 或分配拦截器与计时重叠。
- 会话实际读回值为 init_chunk_size=32，max_chunk_size=1024/32，vectorized=1/0。尝试设置 init=1024 会被两版共同约束为 32。图中数字指会话配置，不能等同每个物理批次的精确大小；EXPLAIN ANALYZE 的实际行数与 loops 全部保留。点查返回一行，也不自动等同所有调用都走标量入口。
- JSON 列目前被两版 Rust 节点的现有存储解码器拒绝，原始拒绝与表均留有证据。测量表为真实 SQL 派生的可读类型表，JSON 组合从实际 id 构造 JSON_OBJECT，未声称测量存储 JSON 列。

主矩阵 270 格、52060 条计时查询；后台负载 32 格、1605 条；并发 36 窗口、26608 条。数值使用各轮格内中位数的中位数；比值使用配对轮比值的中位数。p95 是每格经验 p95 的中位数；三轮范围不当作置信区间。

## 开销来源及下一步顺序

另行进行的、不参与延迟数据的计数测量显示：

| 4096 行查询 | native / 当前分配请求次数 | native / 当前外部复制字节 MB |
| --- | --- | --- |
| integer | 6084 / 89661 | 3.87 / 8.20 |
| nested_integer | 7033 / 275274 | 4.20 / 19.96 |
| json | 326281 / 1413095 | 5.14 / 383.80 |

这些是整个前端进程的 malloc/calloc/realloc 请求及动态 libc memcpy/memmove，包含 RPC、运行时、结果编码和背景活动；不包含编译器内联复制，不冒充纯表达式传输或总堆内存。累计 realloc 请求字节会多次计入新容量；嵌套整数当前约 28.7 GB 的累计请求绝不代表同时占有或实际复制了 28.7 GB。RSS、外部复制量和请求量分别记录。

未启用拦截器的 99 Hz 用户态 CPU 采样中，JSON 的 EvalFrame::storage 约 9.3%、memmove 约 8.7%、帧驱动约 6.2%；嵌套整数的 collect_window_source_charged 约 9.1%，同时出现 realloc、输入读取和 logical_rows_struct。百分比仅是这次短采样的观察；没有把 profile 百分比当作精确可相加的优化收益。

建议按以下顺序继续优化同一个 SDK：

1. 先处理反复增长和临时值/能力句柄传递：整数链的分配请求显著高于 native，优先减少重复 reserve_exact、元信息复制和窗口转换。必须保持真实容量核算、64 MB 限额、来源认证和错误先后；不能简单改为更大的预分配而让原本成功的边界输入提前失败。
2. 把帧及任务的重复存储遍历改为经过验证的增量核算，并继续在上下文回调后复核有效性。以现有取消、异常、缓存退休、opaque cause 与原始记录测试约束它。
3. 在同一 SDK 中继续减少 typed 值与临时字节载体之间的转换。保留真实 FieldType、i128 中间值、NULL 与数据源所有权；不恢复 native 快捷执行器。
4. 每一项之后重跑固定行为对照、实际 SQL 及同样的性能协议。当前数据支持优先优化执行框架边界，不支持把所有时间归因于具体算术或 JSON 算法。

直接依赖构建成本有此前独立目标目录的 M6 记录：四个 SDK crate 的 locked dev check 为 10.19 秒 wall、最大进程树 RSS 1,472,560 KB；这是历史、本机 debug 记录，不冒充当前冷 CI 成本。当前服务器构建与源快照另外完整保留，其中有 Cargo 锁等待，不能用 native 6m33s 与当前 9m16s 直接推导编译回归。单行实际 SQL 及独立分配记录补充了宽度一和传输成本。

## 限制、清理和评审

- 既有完整测试失败保持原样，未删除、忽略或修改原始摘要。两版真实服务器都出现既有 stats-reloader 的负表 ID / AlreadyReg 背景 panic，以及部分关闭时 region-cache 所有权错误；前景 SQL 对照完成，但不能因此宣称生产发布就绪。
- 单机、dev 存储、有限 SQL/输入和少量独立轮次限制结论范围。没有全 workspace 通过、生产压测、完整 Go package 转创或独立第三方代码评审的声明。
- 所有自建 SQL、PD、TiKV、后台负载和客户端进程已停止，八个端口释放，私有临时测试凭据已删除；原工作树的无关 BUILD.bazel 保持不动。
- 源码及行为数据可交付人工评审。统一与去回退的工程验证已完成；性能提升未达成，后续优化优先级如上。
