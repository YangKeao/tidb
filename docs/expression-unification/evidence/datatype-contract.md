**Canonical bounded-domain tail proof (source/index bound, not a new runtime sweep):** assume nonzero operands with canonical leading partial words and I_L+F_L<=n, I_R+F_R<=n. Let A=ceil(l_prec/9), B=ceil(r_prec/9), JL=A−F_L, JR=B−F_R. Leading nonzero word digit widths dL,dR are1..9; c=(left head>=right head), h=1−c. Canonical word order implies ceil((dL−dR+c)/9)=c, hence full integer iterations Q=max(JL−JR+c,0). With N actual iterations and carry restoration δ∈{0,1}, scratch cursor p=N+h−δ>=0 and signed remainder integer words J=JL−p. For uncapped Q>0, J=JR−1+δ<=JR; for Q=0, J<=JL<=JR. If the legacy sentinel caps Q, N=n+1 and JL<=n, so J<=0. Also J<=JL. Thus positive remainder integer words are at most min(I_L,I_R). With F=max(F_L,F_R), min(I_L,I_R)+F<=n. The legacy tail tests positive integer words plus copied fractional words, which are at most F (a leading fractional gap only reduces the copy). Therefore its >n tail cannot be reached by canonical <=n-active-word operands. Zero operands bypass this calculation. This does **not** cover malformed partial-leading-word physical headers or expanded/noncanonical diagnostic shapes; do not infer full physical-transport arithmetic equivalence. No Fixed correction follows automatically from this bound.

## 1. Source map and metadata invariants

### SQL FieldType must remain authoritative

`D/field_type/mod.rs:506–532` defines `FieldType { code, flags:u64, flen:i64, decimal:i64, collation, charset_name, collation_name, elems:GoSharedSlice<GoString>, elems_is_binary_literal:GoSharedSlice<bool>, array }`. Preserve every field, including raw unknown flags and exact charset/collation spellings. `PartialEq` and `Hash` include the source metadata (`:534–567`), not merely the evaluation class.

Important traps:

- `flags()` narrows with `as u32`; `raw_flags()` retains the full word (`:664–676`). Use the latter for the checked projection and cache identity.
- `code()` yields JSON for ARRAY while `array_element_code()` retains the actual element code (`:616–628`). ARRAY is not equivalent to ordinary JSON.
- `FieldType::clone()` shares mutable Go slice backing. Freeze a `deep_copy_like_go()` snapshot (`D/field_type/clone.rs:35–52`) for a compiled specialization. This preserves logical metadata; it intentionally does not preserve aliasing of the original mutable slice. Empty slice allocation/capacity is not an evaluator discriminator. If a future caller requires that distinction it must remain at the host API boundary.
- `K/def/field_type.rs:354–397`: TiKV accessor `tp()` silently substitutes Unspecified for an unknown raw type, `flag()` uses `from_bits_truncate`, and `set_flen`/`set_decimal` narrow `isize` to `i32`. Do not use these as validation.
- `K/def/field_type.rs:54–74`: `FieldTypeTp::from_i32` includes vector code `0xE1`; `from_u8` does not. Use explicit named matches or checked `from_i32`, not enum-discriminant casts or that `from_u8` convenience method for vector.
- Existing remote TiDB `field_type_to_pb` (`DB/rust/crates/tidb-expr/src/pushdown_catalog.rs:2518–2536`) uses narrowed flags and element `.to_string()`. It is not a lossless local bridge; it also belongs to remote admission/serialization, which must not be widened implicitly.
- TiDB's protobuf model is `tidb_proto::tipb` (prost-shaped optional fields); TiKV uses its own `tipb` (rust-protobuf accessors). Copy fields explicitly at the integration boundary. No transmute, serialize/parse hot loop, or assumption that the two Rust types are identical.

Preserve `-1` unspecified metadata; do not supply invented defaults. Set raw PB flags without dropping unknown low bits. A failed checked width conversion is an explicit transport/admission failure; never truncate the SQL metadata to make it fit. High flag bits stay in the SQL type even if the initial kernel projection cannot accept them. Broader metadata-only flag projection requires an explicit approved rule, not an accidental cast.

The signed wire collation ID is supplied by Foundation A/Integration D's checked mapping and remains signed (46 and -46 are distinct). Keep exact charset spelling; do not silently default an unresolved name. Copy losslessly representable PB element/array fields, but keep the full source metadata too. Initial admission excludes ARRAY, ENUM/SET/hybrid semantics, unknown type codes, and nonrepresentable element strings until their domains are implemented. This is partial coverage, not a claim that those types are unused. Foundation B does not edit collation mapping or its files.

## 3. Decimal: present contracts and gaps

### Representations and three independent scales/shapes

`D/decimal/mod.rs:99–170,550–701` stores an ASCII coefficient in SmallVec, sign, visible `scale`, `storage_scale`, and optional declared `(flen,decimal)`; `coefficient_digits()` is explicitly interpreted at **storage_scale**, not visible scale. `D/mydecimal.rs:67–87` is a separate fixed 40-byte cell: signed i8 digit counts/resultFrac, bool sign, nine i32 base-1e9 words. It already implements independent parse/round/shift/compare/conversion algorithms; retaining them all after replacing only Decimal arithmetic would leave duplication.

TiKV `K/codec/mysql/decimal.rs:919–952` is a fixed 40-byte `repr(C)` core with u8 `int_cnt`, `frac_cnt`, `result_frac_cnt`, bool sign, and nine u32 words. `frac_cnt()` and `prec_and_frac()` are public; `result_frac_cnt()` is **cfg(test)-only** (`:1748–1751`). `prec_and_frac()` is natural storage precision, not the SQL column declaration. SQL declaration DECIMAL(M,D), stored fraction digits, and visible result fraction count must all survive independently.

Same byte size is not an API. `read_decimal_from_chunk` (`:2293–2300`) unsafely copies 40 bytes, including bool, without checking counts or words. Do not use it to import TiDB values. TiDB's checked `MyDecimal::from_raw_bytes` (`D/mydecimal.rs:1880–1911`) validates bool, nonnegative counts, used-word count, and used-word ranges; its unchecked `from_raw_bytes_like_go` has a deliberately broader raw-storage contract. A checked evaluator importer must not inherit unchecked storage assumptions.

### Status and operation policy

TiKV `Res<T>` (`K/codec/mysql/decimal.rs:27–110`) carries the result even on Truncated/Overflow. Its `.unwrap()` returns all three values without complaint; `From<Res<T>> for Result<T>` instead discards non-Ok values and errors. Neither is a universal TiDB compatibility mapping.

Core operations already exist: `&a + &b`, subtraction/multiplication => `Res<Decimal>`; `div(rhs, frac_incr)` and `%` => `Option<Res<Decimal>>` (None is division by zero); `round`, `shift`, `as_i64`, `as_u64` preserve status. Keep these exact existing return types for the shared primitive layer; no new duplicate arithmetic trait/status framework is necessary. Match all variants and route policy once at the caller's actual semantic boundary.

Examples of existing policy differences to preserve/audit:

- TiKV expression DecimalPlus/Minus use `Res -> Result` (`KV/components/tidb_query_expr/src/impl_arithmetic.rs:112–120,203–211`), Multiply accepts Truncated (`:319–324`), Div/Mod use context handlers (`:299–309,498–510`). TiKV SUM/AVG `summable.rs:24–54` ignores ctx and treats truncation as error. Sharing those consumers' policy indiscriminately is wrong.
- TiDB `compute_plus` accepts Decimal Truncated and rejects Overflow (`D/datum_eval.rs:70–76`); hash-aggregate paths also use unbounded `Decimal::add`, while window paths use `add_mysql/sub_mysql` with their own handling. These are real external consumers, not only scalar tests.
- TiKV `RoundMode::HalfEven` is a misleading name: implementation uses first discarded digit >=5, hence half-away-from-zero, not banker rounding (`decimal.rs:1253–1283`). TiDB expects -15.5 -> -16, truncate -15.9 -> -15 (`decimal_tests.rs:533–557`). Do not add ties-even behavior because of the enum name.
- TiKV RoundMode::Ceiling's non-word-aligned branch examines only the immediately discarded digit; the TiDB source-backed wrapper intentionally preserves that quirk (`D/decimal/mod.rs:1555–1597`, `decimal_tests.rs:1130`). Mathematical ceiling is not a drop-in replacement.
- `Res::Truncated` is primarily fixed-buffer disposition, not an automatic warning on every ordinary rounding operation. Casting/assignment may separately diagnose loss of nonzero fractional digits. SQL warning code/message/order cannot be inferred from `Res` alone.

### Concrete source-predicted incompatibilities requiring baseline tests

1. **Zero product scale:** TiDB `decimal_tests.rs:1175–1225` expects `0.000 * -1 -> "0.000"`; TiKV `do_mul` resets a negative zero product to `Decimal::zero()` (`:891–899`), dropping its result/storage scale. Predicted TiKV output is `"0"`. Add the focused regression before changing TiKV. Normalize the sign of a successful zero product without resetting the result scale; preserve error-path negative zero (next case).
2. **Overflow negative zero:** TiDB `decimal_mul_overflow_preserves_negative_zero` (`:1231–1237`) expects `(-10^60) * 10^60 -> Overflow, -0, is_negative=true`. TiKV sets the sign before its early Overflow return (`:822–828`). An importer or normalizer that always erases negative zero will break the contract. Preserve sign/status; zero equality/hash policy also needs focused coverage rather than blanket canonicalization.
3. **Hidden precision:** TiDB `division_keeps_word_precision_beyond_display_scale` (`:517–527`) computes 8/7 and 9/7 at increment 7: display 1.1428571 and 1.2857143, but AVG is **1.21428571350000**, not the mean of the displayed strings. For 8/7: coefficient 1142857142, storage scale 9, visible scale 7 (`:561–570`). TiKV `div` records result_frac independently (`:1733–1740`); preserve the actual words throughout SUM/AVG, chunk/spill, comparison, and codecs.
4. **Wide public values:** TiDB `from_literal` and unbounded `add/mul` can exceed nine words. Tests `chunk_bridge_lossy_clamps_integer_overflow_like_go_from_string` and `...excess_fraction...` (`:661–740`) deliberately use 100-digit integers, 101 fractional digits, and a hidden-precision product. Go-like chunk conversion keeps the low 81 integer digits on overflow and the leading available fraction words on truncation. A 10^81 input clamps to zero at that later boundary (`:748–755`). Rejecting or clamping at literal construction changes observable behavior. These contracts remain unmigrated, not silently redefined.
5. **High result scale even within nine words:** TiKV public `round` clamps requested fraction to 30 (`decimal.rs:1172–1190`) and Display calls it (`:1970–1976`). A nine-word parts transport alone does not solve display/rounding domains 31..81 (or unusual raw resultFrac values). Do not conflate SQL DECIMAL declaration limits with raw core capacity.
6. **Codec failure disposition:** TiDB `Decimal::from_bin_with_failure` retains zero receiver and consumed length on bad input (`D/decimal/codec.rs:66–82,557+`). ## 4. Minimal TiKV Decimal extensions proposed

Add in the existing numeric owner `KV/components/tidb_query_datatype/src/codec/mysql/decimal.rs`; parent handles reexports. All names below are proposals. Keep wire/chunk layout unchanged.

```rust

pub struct DecimalParts {
    pub int_digits: u8,
    pub frac_digits: u8,
    pub result_frac_digits: u8,
    pub negative: bool,
    pub words: [u32; 9],
}

impl Decimal {
    pub fn try_from_parts(parts: DecimalParts) -> crate::codec::Result<Self>;
    pub fn to_parts(self) -> DecimalParts;
    pub fn result_frac_cnt(&self) -> u8; // remove cfg(test), no behavior change
}
```

`try_from_parts` validates before indexing: `ceil(int_digits/9)+ceil(frac_digits/9) <= 9` (compute in usize, not overflowing u8); each used word <1e9; partial leading integer word fits its digit count; unused lower digits of the last fractional word are zero. Preserve inactive words verbatim rather than requiring zero, since core operations may retain inactive capacity; they are not additional numeric digits. Initially admit result count 0..=81; reject other raw-storage shapes explicitly rather than normalize them. Result count is independent of storage fraction (do not require equality; padding/display and later raw contracts need their own admission). Preserve sign even for zero. No SQL 65/30 clamp, no parse, round, division, statement context, or warning emission. Export returns the actual stored fields, not `prec_and_frac()` plus reconstructed words. For imported SQL values use canonical active words; for every core operation's status payload verify export→import identity and safe later use. If an existing operation emits a shape outside these invariants, resolve that at the single core owner before routing it; do not conceal the discrepancy in the adapter.

The Rust `DecimalParts` is a logical in-process API, **not** a promised FFI or raw-memory layout. Decode a physical MyDecimal's fields/words explicitly using checked integers/endian operations; never reinterpret the struct or unsafe-copy a bool. For exact evaluator migration, convert only representable values and carry `declared_shape` separately. An out-of-domain result is an unfinished coverage domain, not an arithmetic fallback.

Final host value shape, once the relevant domain is ready:

```rust
pub struct Decimal {
    value: tidb_query_datatype::codec::mysql::Decimal,
    declared_shape: Option<(i64, i64)>,
}
```

No coefficient string, separate sign/scale numeric mirror, or duplicate add/mul/div/round code in that wrapper. Forward sign, result scale, storage fraction, compare, and numerical conversion to the shared core. Metadata policy (copying/clearing declared shape, mapping a disposition into an existing host error type) can remain host-side.

Additional narrow helpers should be added **only when migrating their concrete consumers**:

- Checked coefficient/i128 import/export on the TiKV core, preserving both fraction counts (`try_from_scaled_i128`, `coefficient_i128` equivalent). `fold_coefficient_i128` must decline hidden digits as TiDB currently does. Initially remove host i128 arithmetic fast paths rather than port a new accumulator framework; optimize only inside the single TiKV numeric owner after correctness/performance evidence.
- Natural storage precision and canonical key/payload encoding supplied by shared words, avoiding host digit math. Existing `prec_and_frac`, DecimalEncoder/Decoder, and Hash are starting implementations, but Hash is not TiDB's stable byte-key protocol. Add payload-only/status-bearing entry points only for proven missing byte contracts, reusing the existing encoder algorithm.
- An explicitly selected non-clamping result formatter/rounding core for the source raw scale domain if required. Do not change every SQL ROUND's bound to solve raw presentation. Keep one rounding algorithm with an explicit bound at the appropriate wrapper.
- Preserve zero-product scale in `do_mul` without erasing Overflow's signed-zero payload. This is a focused behavior extension, not a host fixup after every multiplication.
- Diagnostic-rich decimal decode only if the malformed-input baseline requires it: consumed length + result/status on soft failure, clear invalid-data error on hard failure; do not weaken the existing wire reader silently.

**Important source API issue:** `Decimal::coefficient_digits(&self) -> &str` cannot retain that borrowed return type with only a fixed-word core and metadata, unless a numeric string mirror/cache is added (not proposed). Change concrete internal consumers to shared precision/key helpers or an explicitly owned rendering accessor when rendering is truly required. Parent must approve this internal Rust API adjustment; do not disguise it as keeping every Decimal API identical. Public FieldType/Datum/Expression shape stays preserved.

## 6. Later domains: exact transport, not semantic re-evaluation

### DATE/DATETIME/TIMESTAMP and TIME duration

TiDB `D/mysql_time.rs:164–211,292–338` retains calendar fields, TimeType and FSP; bit-width-checked construction can carry zero/invalid calendar dates. Its Go raw layout is not the wire packed datetime layout. TiKV `K/codec/mysql/time/mod.rs:167–196` packs the same logical fields, but existing `from_slice` calls SQL validation (`:1724–1746`) and `from_packed_u64` interprets a Timestamp as UTC and converts into session TZ (`:2009–2048`). The local bridge must use neither for already-local values. The chunk decoder (`:2962–2966`) is an unchecked raw convenience, not the checked logical API.

Minimal proposed TiKV additions (same existing file; parent controls publication):

```rust
impl Time {
    pub fn try_from_local_components(
        parts: [u32; 7], // year, month, day, hour, minute, second, microsecond
        time_type: TimeType,
        fsp: u8,
    ) -> crate::codec::Result<Self>;
}
impl Duration {
    pub fn try_from_local_parts(nanos: i64, fsp: u8) -> crate::codec::Result<Self>;
}
```

Time import checks storage field widths before packing (14/4/5/5/6/6/20 bits) and FSP 0..6 (DATE requires its source FSP 0); it does **not** apply year<=9999, calendar validity, zero-date SQL mode, timezone, timestamp range, or current clock. Preserve every supplied calendar field even for DATE, rather than erase hidden time fields via a type-changing setter. Existing `year/month/day/hour/minute/second/micro/get_time_type/fsp` getters suffice for export, followed by TiDB `Time::from_date_checked`. Semantic use still validates as its actual operation requires. Out-of-range raw FSP metadata remains explicitly unmigrated.

TiDB `MySqlDuration::from_nanoseconds` does not round (`D/duration.rs:68–79`); TiKV `Duration::from_nanos` does (`K/codec/mysql/duration.rs:446–449`). Initial exact Duration importer preserves nanos and validates FSP and existing safe duration range `[-MAX_NANOS, MAX_NANOS]` without rounding. Sub-FSP retained nanoseconds (e.g. 1_234_567_000 with FSP=3) must survive the bridge unchanged. Wider/raw TiDB durations and arbitrary i64 FSP have broader storage contracts and stay separately unmigrated, not clamped. Reverse uses exact `to_nanos/fsp` and TiDB `from_nanoseconds`. Parser/CAST rounding belongs outside transport.

Regression cases: zero date under strict/no-zero SQL modes in a dead branch; nonzero local Timestamp transported under UTC and +08:00 without changing wall-clock fields; DST-fold/gap values not resolved during compile; DATE versus DATETIME tag; FSP=6 with microsecond=1; negative duration and retained sub-FSP fraction. Context/TZ/error policy is Runtime C ownership.

### JSON

TiDB BinaryJSON has exact type-code/payload accessors (`D/binary_json.rs:168–254,296–311`). TiKV `JsonType::try_from(u8)` is checked, but `Json::new` and `JsonRef::new` merely store bytes (`K/codec/mysql/json/mod.rs:128–165,314–321`); internal readers assert/index assuming validity. TiKV `JsonDecoder::read_json` does not recursively validate nested offsets and even inspects short container slices before proving their size (`.../jcodec.rs:237–268`). Do not call those unsafe-in-practice readers on unchecked raw TiDB `from_encoded_parts` payloads and call the bridge checked.

Use type-code + unchanged binary payload, not JSON text/serde conversion (which can change U64/Double/opaque/temporal types). Proposed later minimal core API: `Json::try_from_binary_parts(type_code: u8, payload: Vec<u8>) -> crate::codec::Result<Json>`, validating tag, exact payload extent, safe offsets/lengths, literal codes and nested structure without normalizing numeric tags or object order. One TiKV validation implementation should serve all importers; do not add a second host JSON parser. Malformed lazy values require demand-safe handling. SQL NULL = `Json(None)`; JSON null = `Json(Some(Json::none()?))`.

Operation differences are concrete, not solved by this transport:

- TiKV double comparison uses `f64::EPSILON` for Double/Double too (`.../json/comparison.rs:23–28,91–120`). TiDB compares two doubles exactly and uses **1e-8 only for integer/double** (`D/binary_json.rs:59–61,927–965`). Thus Double(0.0) vs Double(1e-20): TiDB Less, TiKV source predicts Equal; Int(1) vs Double(1.000000001): TiDB Equal, TiKV source predicts Less.
- TiKV object comparison uses raw payload bytes; TiDB compares member count then sorted keys and recursively values (`D/binary_json.rs:798–839`). `{"a":255}` vs `{"a":256}` has opposite low-byte order for the little-endian integer payload versus numeric order. Add a precise fixture before migration.
- Opaque and temporal JSON carry distinct codes/bytes, not normal JSON strings. Preserve them when testing comparisons, casts, grouping and persistence.

Ordinary JSON stays a migration objective; these examples require a fix in the one shared kernel owner, not blanket deferral of the family.

### VECTOR<FLOAT32>

TiDB stores aligned f32 elements; validated constructors reject nonfinite values, but `elements_mut` and raw decode can retain arbitrary bits (`D/vector.rs:43–53,77–89,114–123`). Wire serialization is length-u32-LE plus f32 bits (`:157–169`). TiKV stores the element bytes **without** that length header and checks finite/aligned-sized input (`K/codec/mysql/vector.rs:12–45,71–91,127–146`).

For the initial finite domain use checked `VectorFloat32::from_f32` (or `VectorFloat32Ref::from_f32` only when lifetime is explicit), preserving each f32 bit. For reverse conversion use the existing wire encoder into bytes and TiDB's exact wire decoder, or a checked element-by-element export helper if profiling later warrants it; no f64/text widening. Do not hand the length-prefixed TiDB byte slice to TiKV `new`, which would treat the header as an element. Check declared dimension separately with source rules. TiKV wire decoder requires little endian. Raw nonfinite payloads and platform endianness are explicit remaining domains. Do not use derived byte equality/hash as a substitute for SQL element comparison, especially ±0.0.

## 9. Risks and stopping state

Measure after correctness; reuse scratch/compiled state; do not restore native algorithms as a performance escape.
