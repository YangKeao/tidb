## One implementation authority

The public native exact div/rem SDK becomes a thin bridge to TiKV's existing IntegerPair/Grow division core, preserving the original right-zero guard before left input conversion, quotient scale0, independent remainder storage/result scales, signs, zero normalization and fresh shape. The budgeted legacy quotient uses the existing RetainedQuotient request with zero fraction words; it is not a new bounded-pair algorithm. Native digit_divmod and pad_scale remain for other consumers, including div_round; no AVG or unrelated arithmetic expansion is claimed.

Native bounded Decimal DIV becomes one guarded worker invocation. Borrowed actual Decimal identity views feed shared demand classifiers before encoding allocates operand frames. The original raw0/1/2 precision reads are retained independently, including effective0→4, matching storage scales<=3, eager coefficient projections and canonical-magnitude versus signed-raw-text i128::MIN behavior. Caller pre-reads remain untouched. Native is_zero is UTF8 decoding followed by all-zero-byte iteration, including the empty string, not equality with a single zero byte; an early parent assumption was corrected from source before implementation.

Two fixed native profiles take the existing BytesIntIntBytes carrier: actual left/right raw Decimal frames and optional actual probe/fallback u32 reads widened losslessly to i64. Only these profiles project four semantic fields into five physical operands with the existing finite resource budget. Their strict shared predicate validates demanded presence and range at both boundaries. A narrow existing-facade projection wrapper deducts observed retained storage and actual frame capacities, reuses the old finite-budget helper and leaves old carriers/projections unchanged. The additional compile whitelist arm only permits these two Values/arity5 profiles; no new driver, carrier, result kind or RuntimeBinding is introduced.

TiKV performs both fast checked division and bounded DecimalDiv, the original nine-word truncated-quotient adjustment, integer conversion, unsigned small-negative-fraction rule, and warning formatting. The existing OwnBytes result contains a strictly decoded actual outcome and optional actual complete warning text. Native code only replays the warning first, then division-by-zero/NULL, Int/UInt bits or integer overflow. Infrastructure/count/allocation failures are never repackaged as SQL overflow. The `/` profile's extra scale-plus-increment transform is not reused.

Legacy exact Decimal DIV uses existing Bytes2 raw frames, not a preconverted Decimal2 pair. This revision is necessary to retain actual zero RHS before validating an invalid LHS: a worker must produce the NULL result, not a frontend placeholder, NullWitness or cached answer. The same narrow budget projection appends a third physical operand for this one profile. The worker checks the original RHS zero predicate first, then uses the shared exact retained quotient and maps signed-i64 overflow to NULL. Native only widens the actual result to i128. Original tuple child demand, child SQL folding, typed-Decimal admission and getter/warning absence stay; the previously migrated legacy integer MIN/-1 panic is a distinct policy.

## Explicit representation-domain limitation

The raw identity constructor is lossless representation transport, not admission to all arithmetic. A known pre-existing defined edge is not claimed equivalent here: `from_raw_parts(false, empty, 0, 0) / 1` previously produced exact quotient/remainder zero; the shared math bridge rejects the empty coefficient. The infallible public SDK consequently panics, while the legacy evaluated path reports infrastructure failure rather than zero. No native fallback is retained to conceal this difference. Valid arithmetic values, including hidden fractional storage, are the current functional domain. Zero RHS still takes precedence over an invalid LHS; this priority is preserved explicitly rather than swept into the limitation. Full invalid-raw mathematical parity remains deferred and prevents strict-completion claims.
